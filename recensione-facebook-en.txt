I've been running a SMLIGHT SLZB-Ultima3 as my Zigbee coordinator for Home Assistant for a few months now, and since this group often discusses how to manage non-trivial Zigbee networks, I figured I'd share a somewhat more technical write-up of what I found — code included, for anyone who wants to replicate it.

The starting point is structural, not cosmetic: the Ultima3 doesn't expose a single Zigbee coordinator but three independent radios, each with its own firmware, its own restart button, and its own update entity in Home Assistant. I'm using two of them. Radio 1 is assigned to ZHA and handles devices that can lose power at any moment — in particular, several Zigbee bulbs wired downstream of Bticino Living Now Smart switches: when the relay opens, the bulb loses power entirely, so I'd rather keep these devices on their own separate stack. Radio 2 is assigned to Zigbee2MQTT and handles sensors, buttons, and thermostatic valves — devices that are always powered or battery-operated, where mesh stability over time matters most.

Under the hood, the two built-in radios aren't identical chips. The first is a Texas Instruments CC26xx, the second a Silicon Labs EFR32MG. Both are multi-protocol radios: each can independently run as a Zigbee coordinator or router, or as a Thread Border Router for Matter devices — so in theory I could use one of them for a Thread network instead of Zigbee2MQTT, I just haven't needed to yet. The main SoC orchestrating everything else — Ethernet, 2.4 GHz Wi-Fi, Bluetooth as a BLE proxy for Home Assistant (if running ESPHome), and the network backbone for all internal and external radios — is an Espressif ESP32-S3. There's also a USB host port for an additional external radio (a Zigbee, Thread, or Z-Wave dongle): a way to pair the built-in radios with an independent Thread network. In my case, though, that port is already taken by the 4G module — the datasheet says so explicitly, the two add-ons share the same USB slot and you can't have both at once. Anyone without the 4G module can use it freely. There's also an optional Z-Wave 800 add-on (not yet certified, work in progress), managed via Home Assistant's Z-Wave JS over Ethernet or USB — which is exactly the third radio slot Home Assistant shows me beyond the two built-in radios (third restart button, third firmware update entity): I have that one installed too, but I'm not using it yet, same story as the 4G module.

My setup currently has 17 devices on ZHA and about 46 on Zigbee2MQTT, physically split across two separate radios rather than two software processes sharing the same chip: updating one radio's firmware doesn't touch the other in any way. The practical benefit goes beyond firmware isolation, though: since they're on physically different radios, ZHA and Zigbee2MQTT also each get their own Zigbee channel (2.4 GHz band, channels 11-26), with zero overlap between the two networks — two fully independent PANs, each with its own channel, PAN ID, and network key, so there's zero airtime contention between them. With close to seventy devices in total, having two smaller networks instead of one large one also helps routing tables and mesh depth, and lets you pick a channel for each that avoids overlapping with your home Wi-Fi (Zigbee channels 15, 20, and 25 are generally the cleanest relative to Wi-Fi channels 1/6/11).

The rest of the hardware package is generous: Ethernet with PoE power (a single cable for both data and power), Wi-Fi as a backup link, a built-in piezo buzzer, an Ambilight LED strip (WS2812B, the same addressable LEDs used across half the maker world), an IR transmitter and receiver capable of learning codes from existing remotes, an I²C bus with free GPIO for sensors or custom hardware, and, on my unit, a 4G module I haven't activated yet: it just sits there as a connectivity failover for anyone who needs one.

On the Home Assistant side, the official smlight integration is a local, push-type connection and exposes a solid set of diagnostic entities: main chip temperature, temperature of each Zigbee chip, RAM/filesystem/PSRAM usage percentages, separate uptime for the core and for the Zigbee side, Ethernet/Wi-Fi/Internet/VPN status, and an update entity for every firmware (core plus three radios, four entities in total). That VPN entity is a built-in WireGuard: a direct, secure tunnel to Home Assistant without opening ports on your router, plus an optional DDNS for anyone with a dynamic public IP — I haven't set it up yet, but it's there ready to go.

What surprised me most, though, was something else entirely: underneath the Home Assistant integration, the Ultima3 runs SLZB-OS, a firmware with its own scripting engine built on Berry, a Lua-like embedded language designed for microcontrollers. The runtime supports up to three concurrent scripts, with a default 5120-word stack for "free-running" scripts and a shared task for event-driven ones, where each handler gets a 500-millisecond execution budget. Around the language sit more than fifty native modules: MQTT, HTTP, Telegram, buzzer, IR, Ambilight, GPIO, ping, plus direct integrations with services like Home Assistant, Discord, Pushover, and ntfy. In practice, the gateway can automate itself, entirely independent of Home Assistant — handy if the server is ever down for maintenance or some issue of its own, since the gateway still needs to notice when something's wrong. SMLIGHT states this explicitly in their product material — "no cloud, ever" — and fittingly there's also an "Internal Zigbee Hub" mode that runs a lightweight Zigbee2MQTT/ZHA-style hub directly on the device, with no external server: for anyone who wants a minimal setup (a few lights or sensors) without even bringing Home Assistant into the picture. That's not my case, but it's a good sign of how self-sufficient the device is meant to be. A nice side note: the product is engineered in Ukraine, something the manufacturer states openly on their site.

I wrote three scripts to actually put this engine to work.
The first is a watchdog that runs in a loop and checks, radio by radio, the number of clients connected to the Zigbee socket via ZB.getZbClients(index): if radio 1 or radio 2 goes from "client connected" to "no client," it sends a Telegram message via TELEGRAM.send() — deliberately without restarting anything automatically, to avoid a self-feeding reboot loop. The same script checks Internet reachability with PING.alive() and, if the check host doesn't respond for about a minute, it alerts via Telegram and sounds the buzzer with BUZZER.play() in RTTTL format (the same standard from old Nokia ringtones: name, default duration/octave/BPM, then the note sequence). Finally, it checks free RAM via SLZB.freeHeap(), which on the Berry runtime is only available in absolute bytes, not as a percentage.
The second script is a daily status report: uptime, free RAM, and connected clients on each radio, sent to Telegram right at startup and then every 24 hours — just to confirm the gateway is alive without opening Home Assistant.
The third remotely drives the buzzer while staying entirely native: the script on the Ultima3 does MQTT.subscribeCustom() on a dedicated topic and, in MQTT.on_message(), maps the incoming payload to a predefined RTTTL melody, complete with a Telegram confirmation of which sound was played; from Home Assistant, a simple mqtt.publish is enough to trigger it, so all the logic stays on the device and Home Assistant just acts as a remote control.

Ideas for next time: use the Ambilight as a visual status indicator instead of just text notifications — green when everything's fine, blinking red if a radio loses its client; put the IR transmitter, currently completely unused, to work as a small universal remote callable from Home Assistant; finally give the 4G module a real shot as an actual network failover, with a script that alerts when the gateway switches from Ethernet to cellular; and while I'm at it, try out the Z-Wave add-on too — I've got it installed but never wired up to anything — if only to see how it coexists with two Zigbee networks already running on the same device.
